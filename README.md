# ПОС — преподавательская оценка студентов

Учебное консольное приложение для одного курса. В нём можно вести список студентов и рубрикатор, выставлять, исправлять и отменять оценки, смотреть результаты и выгружать ведомость в CSV.

## Запуск

Понадобится Go 1.25.5 или новее. Команды ниже запускаются из папки проекта.

```powershell
go run .
go test ./...
```

Консоль записывает ведомость в `pos.json`. Можно передать другой файл через `-data`. Введите `help` для списка команд. Параметры одной команды разделяются `|`, имя и комментарий могут содержать пробелы. Дробные числа можно вводить с точкой или запятой.

### Демонстрация

Эти команды запускают сценарий в PowerShell со свежим файлом ведомости.

```powershell
$demoData = Join-Path $env:TEMP ("pos-demo-" + [guid]::NewGuid().ToString("N") + ".json")
go run . -data $demoData -script demo.txt
```

Сценарий добавляет двух студентов и два критерия, исправляет одну оценку, отменяет другую, выводит оценки, результаты и аналитику. В конце он сохраняет `results.csv` в текущую папку. Ожидаемые результаты в режиме `final` — **84%** для Анны и **30%** для Ильи. Результат Ильи в режиме `progress` — **50%**, оценён один критерий из двух. При ошибке в файле команд прогон завершается с ошибкой, в интерактивном режиме можно исправить команду и повторить её.

## Доменная модель

| Понятие | Тип и правило |
| --- | --- |
| Студент | `Student` — сущность с идентификатором. |
| Критерий | `Criterion` — сущность рубрикатора с идентификатором, положительным максимумом и положительным весом. |
| Оценка | `Evaluation` — запись с идентичностью по паре «студент, критерий». Повторная установка меняет текущую оценку этой пары. |
| Балл | `Score` — объект-значение без своего идентификатора. Фабрика проверяет, что число конечно и входит в `[0, MaxScore]` выбранного критерия. |
| Ведомость | `Gradebook` — агрегат одного курса. Он хранит студентов, критерии и оценки и проверяет, что студент и критерий существуют перед записью оценки. |
| Итог | `CalculateResult` — доменный сервис. Он использует рубрикатор и текущие оценки, поэтому сразу учитывает исправления и отмены. |

Итог измеряется в процентах по формуле

```text
100 × сумма((балл / максимум критерия) × вес критерия) / сумма весов
```

В режиме `final` знаменатель включает все критерии, у пропущенной оценки вклад равен нулю. В режиме `progress` учитываются только критерии с выставленной оценкой. Выставленный ноль считается оценкой. Для пустого набора учитываемых критериев выводится 0% и показывается число выставленных оценок. Веса относительные, поэтому для них не требуется сумма 100. Округление до двух знаков происходит при выводе в консоль и CSV.

## Clean Architecture

Я выбрал **Clean Architecture** на основе своего проекта [LinkTracker](https://github.com/Br1ght-SuN-lab/LinkTracker), который написал в Т‑Академии. Для ПОС я взял оттуда разделение на `domain`, `application` и `infrastructure`. Для консольного приложения одного курса достаточно одного процесса и трёх пакетов.

```text
main           → infrastructure, application
infrastructure → application, domain
application    → domain
```

- `internal/domain` содержит ведомость в `gradebook.go`, рубрикатор в `rubric.go`, создание оценок в `evaluation.go` и расчёт итога в `result.go`. Здесь проверяются правила предметной области при каждой записи, включая восстановление из JSON.
- `internal/application` содержит сценарии и два порта. `Repository` читает и обновляет агрегат, `ReportExporter` выгружает сформированную ведомость.
- `internal/infrastructure` содержит консоль, JSON-хранилище и CSV-экспорт. При чтении JSON хранилище восстанавливает агрегат через методы домена, которые повторно проверяют инварианты. Изменения файла ведомости сериализуются через файл `.lock`, запись идёт во временный файл с последующей заменой. После аварийного завершения оставшийся `.lock` можно удалить, когда запись уже не выполняется.
- `main.go` собирает зависимости через `go.uber.org/dig`. Консоль получает `Service`, а тот получает реализации портов через конструктор.

## Паттерны GoF

| Группа | Паттерн и место | Что решает |
| --- | --- | --- |
| Порождающий | **Фабрика**, `rubric.newEvaluation` | Создаёт оценку через рубрикатор. В одной точке проверяются существование критерия и допустимый диапазон балла. |
| Структурный | **Facade**, `application.Service` | Консоль вызывает готовые сценарии. Чтение ведомости, расчёт отчёта и передача его в экспортёр находятся внутри фасада. |
| Поведенческий | **Strategy**, `FinalStrategy` и `ProgressStrategy` | Два режима определяют состав учитываемых критериев. Формула расчёта остаётся общей. |

## Как использовался ИИ

Я сам выбрал Clean Architecture, опираясь на [LinkTracker](https://github.com/Br1ght-SuN-lab/LinkTracker), который написал в рамках Т-Академии. Для ПОС я взял из него разделение на `domain`, `application` и `infrastructure` и адаптировал его под небольшое консольное приложение.

Я продумал сущности предметной области и их связи: студента, критерий, оценку и ведомость. Когда `gradebook.go` стал слишком большим, я предложил его разгрузить. С помощью ChatGPT мы разделили код внутри `domain`: работу с рубрикатором вынесли в `rubric.go`, а создание и проверку оценки — в `evaluation.go`. Я объяснил, как понимаю назначение паттернов GoF. На этой основе ChatGPT предложил, где их применить в ПОС: фабрику для создания оценки, Facade для сценариев приложения и Strategy для выбора режима расчёта итога.

Я написал большую часть кода приложения и автоматические тесты.

ChatGPT помог реализовать отдельные компоненты, подготовить черновик README и сверить реализацию со всеми функциональными требованиями ТЗ. Он предложил формулу и два режима расчёта итога, хранение в JSON и синтаксис команд. При проверке ChatGPT запускал автоматические тесты и сквозной сценарий через консоль.
